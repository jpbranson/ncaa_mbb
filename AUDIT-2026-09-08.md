**Method.** Every module in `src/cbbwp/` and every script in `scripts/` was read in full,

## Verdict

This is an unusually disciplined project: one state/feature definition shared by training
and serving, versioned state rules with a load-time refusal, pre-registered bars for
things that were then honestly not shipped, and tests that encode *why* past bugs
happened. The headline claims check out. I would not block release on the modelling.

I **would** block going live on the Mac deployment as installed, because of H1: the
service never reloads the ratings snapshot, so the daily ratings LaunchAgent it installs
alongside itself has no effect on a running service, and `/health` goes permanently
degraded after three days of uptime even when everything on disk is fresh. H2 does not
touch the shipped path, but it invalidates the "measured, observed behaviour" claims
behind the endgame table and quite possibly the table's failed ship criterion.
Everything else below is a fix-soon or a fix-eventually.

## High

### H1. The running service never reloads the ratings snapshot; the installed deployment refreshes a file nobody reads

`serve_live.py` loads the snapshot once at startup
(`scripts/serve_live.py:60`, `LiveContextProvider.load`) and the poller uses that
in-memory object for every game all process-lifetime (`scripts/live_poller.py:138`).
There is no reload path anywhere. Meanwhile `deploy/install_macos.sh` installs:

- `com.cbbwp.live` — **always on** (`KeepAlive` = true, restarts only on crash), and
- `com.cbbwp.ratings` — daily at 09:30, rebuilds `registry/context_latest.json`.

The composition is broken in two ways:

1. **Ratings staleness.** The daily rebuild updates the file; the running poller keeps
   serving the ratings it loaded at startup. Over a season of uptime, every game's
   `pregame_exp_margin`, `ft_pct_diff` and `exp_points_per_min` come from launch day.
2. **Permanent 503.** `/health`'s freshness callbacks close over the in-memory object
   (`scripts/serve_live.py:96-99`), so `ratings_age_days` grows monotonically with
   uptime. After `CBBWP_RATINGS_MAX_AGE` (default 3) days, `/health` returns 503
   "ratings snapshot file is stale; re-run build_live_context.py" — advice that has
   already been followed, by cron, to no effect. The Docker healthcheck
   (`deploy/Dockerfile`) starts failing at the same moment, marking a healthy container
   unhealthy. Out of season this happens too (`file_stale` has no season gate, only
   `data_is_stale` has one — `src/cbbwp/api.py:125`).

The docs half-know this: the *container* doc says "restart the container to pick it up",
but the Mac install — the primary deployment — schedules no restart and the deployment
doc never says the live agent must be bounced after the ratings agent runs.

**Fix (small):** in the poller's discovery loop, stat `cfg.context_path` and re-`load()`
when the mtime changes (the provider is immutable and cheap to rebuild; swap the
reference atomically). Alternatively have the ratings LaunchAgent `launchctl kickstart -k`
the live agent after a successful rebuild — but the reload is strictly better and ~10
lines. Add a test: update the snapshot file, assert the next `context_for` sees it.

### H2. The endgame table's fouling parameters are attributed to the wrong possession — the measured foul–margin relationship is inverted

*(Diagnostic path only — the table is documented as not served. Listed High because it
undermines documented claims, not because it endangers production.)*

`scripts/estimate_endgame_possessions.py:59-101` segments possession "runs" on the
**post-event** possession from the states files. But the state rules flip possession on
every *made* free throw (`state._possession_after`: made FT → other team), so a made-FT
trip's rows carry the defence's possession value and attach to the head of the fouling
team's *next* run; `fouled_to_line = saw_ft & ~saw_made_fg` then flags the wrong run.
The signature is visible in the shipped artifact (`artifacts/endgame_possessions.json`):
in the last 10 seconds, the "offence" **trailing** by 3–7 is recorded reaching the line
71–84% of the time while the offence **leading** by 3–7 sits at 10–18% — exactly
backwards from real endgame play, where the trailing defence fouls the leading
ball-holder. (The leading team's residual 10–18% comes from missed front ends, which
don't flip possession and so stay in the correct run.) `mean_dur_when_fouled` inherits
the same mis-attribution.

The backward-induction solver keys its entire "defence fouls" branch on this grid
(`src/cbbwp/endgame_sim.py:243-281`), so the table simulates leaders never being fouled
and trailers being hacked. That plausibly explains why the table-only log loss (0.1386)
trails the model (0.1220) and why criterion 1 failed at 0.40%. Consequences:

- `endgame_sim.py`'s docstring ("the fouling rule is OBSERVED behaviour"), 
  `docs/cbbwp-endgame-phase2.md` ("measured"), and `docs/cbbwp-endgame-results.md`
  present inverted measurements as observations.
- CHECKPOINT's advice — "Do not rebuild any of these expecting a different answer
  without changing something structural first" — is undermined for the endgame table:
  there *is* something structural to change, and a corrected table could plausibly
  clear the pre-registered 1% bar it missed by 0.6 points.

**Fix:** segment runs on the possession *before* each event (shift by one), or
attribute a trip to the run containing its triggering foul row (`saw_foul` is already
aggregated and unused). Then re-run phases 2–5 against the same pre-registered bars.

## Medium

### M1. Live pregame ratings are not on the training scale (contradicts `build_live_context.py`'s own claim); ~1.3-point sd error in November

`scripts/build_live_context.py` says it uses "the SAME ridge fit … so a live game's
pregame term is on the same scale the model was fit on." The fit function is the same;
the **prior** is not:

- Training (`cbbwp.ratings.build_all_seasons`, `src/cbbwp/ratings.py:106-117`) chains
  priors season over season from 2016, applying `CARRYOVER = 0.70` at every boundary.
- The live snapshot (`scripts/build_live_context.py:29-32`) seeds from a *single*
  previous-season fit with an **empty** prior.

Measured for this audit on the real `games.parquet` (comparing the per-game
`pregame_exp_margin` each method produces for upcoming 2026 games, fitted on games
completed so far):

| fit through | margin discrepancy (sd) | max |
|---|---|---|
| first 2 weeks of Nov | **1.31 pts** | 6.8 pts |
| end of December | 0.23 pts | 1.2 pts |
| full season | 0.09 pts | 0.4 pts |

So in the exact window where the pregame term dominates the model (early season, early
game — before `pregame_exp_margin_decayed` fades), the live path feeds the model a
pregame margin off by ±1.3 points sd, up to ~7 points, relative to what it was trained
on. This is precisely the class of train/serve skew the project works hardest to
prevent elsewhere.

**Fix:** make `build_live_context.py` build its prior by chaining across seasons exactly
as `build_all_seasons` does (it already reads `games.parquet`, which contains every
season; the chain costs a few seconds). Add a parity test comparing the snapshot's
rating for a few teams against the offline chain.

### M2. Feed-disorder detection exists but nothing in the live path calls it

`espn.chronological_inversions` (`src/cbbwp/adapters/espn.py:140`) is the promised
mechanism by which "a disordered feed is a thing somebody is told about rather than
something silently rearranged." Its only callers are tests and the fixture builder;
the poller, `check_espn_fixtures.py` and the smoke test never compute it. If ESPN ever
does deliver a disordered array, the deployed system builds states from it silently —
the one consumer that would visibly notice is the viz page's independent JS `displaced`
logic, which an operator may never open.

**Fix:** compute it in `Poller.watch` after `parse_summary` and log (or count into
`/health`) when non-zero; also print it per payload in `check_espn_fixtures.py`.

### M3. The viz server's score cache is never invalidated — re-fetching an in-progress game returns the stale scored result

`Scorer.score` checks the cache before looking at the payload it was handed
(`scripts/serve_viz.py:92-95`), and `/api/fetch/<id>` fetches a *fresh* payload from
ESPN, archives it, then calls `score(gid, payload)` — which returns the previously
cached result and silently discards the new plays (`scripts/serve_viz.py:221-235`).
Fetching a live or recently-updated game twice in one server lifetime shows no new
plays, with no indication anything is stale. The same cache also hides any edit or
re-archive of an existing file for `/api/game/<id>`.

**Fix:** key the cache on `(game_id, len(payload["plays"]))` or a payload hash, or
bypass/overwrite the cache on the `/api/fetch` path (it holds the fresh payload in
hand — there is no reason to prefer the cached one).

### M4. Replay/smoke rows can still reach `data/live/`, and the live calibration monitor would ingest them

README: "Replay rows are tagged `"replay": true` and written to `data/replay/`, never
`data/live/`." That diversion lives only in `serve_live.py` (`scripts/serve_live.py:82-87`).
Two paths bypass it:

- `scripts/live_poller.py` run directly (its documented usage) defaults `--out` to
  `data/live/wp_<day>.jsonl` unconditionally (`scripts/live_poller.py:272`). With
  `CBBWP_ESPN_BASE` set, tagged replay rows land in the live record.
- `Poller._one` (the smoke test's step 7, `scripts/live_poller.py:218-239`) writes its
  rows raw — no `ts`, no `status`, no `replay` tag even in replay mode — to the same
  live file. This has already happened on this machine: `data/live/wp_20260903.jsonl`
  contains untimestamped smoke rows.

Downstream, `calibration_monitor.py --source live` reads `data/live/*.jsonl` and never
filters on the `replay` key (`scripts/calibration_monitor.py:65-91`), so the tag —
the last line of defence — is not actually consulted by the one consumer that matters.
(Replay rows for archived real games would join to real outcomes and mostly be
duplicates of backtest rows rather than garbage — but the record-of-truth guarantee is
the point, and it is only as strong as its weakest writer.)

**Fix:** move the replay-diversion default into `live_poller.main` (or into `Poller`
itself, keyed on `client.is_replay`); make `_one` emit through `emit()` so rows are
tagged and timestamped uniformly; drop `replay`-tagged rows in `from_live` with a
printed count.

### M5. An unparseable or missing clock becomes `0`, which the endgame clamp turns into near-certainty mid-game

`clock_to_seconds` returns 0 for anything it cannot parse (`src/cbbwp/state.py:39-50`),
including the empty string ESPN sends when a play carries no clock
(`tests/test_espn_adapter.py:79` pins this). For a period-1 play that yields a harmless
mid-game 1200s. For a **period-2 or OT** play it yields `game_seconds_remaining = 0`,
and `endgame.apply` then declares the game over — clamping the emitted probability to
0.999/0.001/0.5 (`src/cbbwp/endgame.py:29-33`) on a game that may have ten minutes
left. One malformed `displayValue` in the live feed produces an absurd published
number, and nothing logs that a clock failed to parse. The 0.2% of contradictory feeds
already observed (EXPLAIN §7.8) shows malformed payloads are not hypothetical.

**Fix:** distinguish "unparseable" (return `None`) from a real `0:00`; carry the
previous event's clock forward for `None` (matching the possession rule's "carry"
philosophy) or at minimum count parse failures per game and surface them the way
unknown play types are surfaced.

> **Resolved partially, on purpose.** `state.parse_clock` now returns `None` for
> an unreadable clock, `espn.clock_parse_failures` counts them, and the poller
> and `check_espn_fixtures.py` report them — the audit's own fallback option.
>
> The carry-forward half is **not** done, and should not be done casually.
> Carrying the previous clock forward changes what `game_seconds_remaining`
> MEANS for affected rows, which by this project's own doctrine
> (`STATE_RULES_VERSION`, `schemas.py`) requires a version bump and a refit —
> invalidating `registry/v2` and every number in the checkpoint. That is a
> deliberate decision with a real cost, not a bug fix, and it belongs to whoever
> owns the release rather than to an audit follow-up. The detection added here
> is what tells you whether it is worth paying: on every payload measured so
> far the count is zero.

### M6. No CI

`tests/test_replay_harness.py` says of itself "this belongs in CI"; there is no CI
configuration in the repository (no `.github/`, nothing else). The 111-test suite —
including the parity tests that guard the project's central invariant — runs only when
someone remembers to run it (the smoke test runs it, but the smoke test is also manual).
For a project whose whole safety story is "the tests catch skew," the tests need to run
on every push.

**Fix:** a minimal GitHub Actions workflow running `pytest -q`. The data-dependent tests
skip cleanly when parquet is absent (verified in the skip guards), so CI without the
527 MB of data still runs the ~40 pure tests; a scheduled job with cached data could
run the rest.

## Low

### L1. `publish_model.py` publishes whatever `gbm_v1.txt` happens to be, and nothing ever verifies the manifest hash

`scripts/publish_model.py:10` copies `artifacts/gbm_v1.txt` regardless of the version
argument, so `publish_model.py v3` publishes the most recent fit under any name —
there is no binding between the version label and a particular fit beyond operator
discipline. The manifest's `sha256` (truncated to 16 hex chars) is written but never
checked: `WinProbabilityService` verifies features and state rules but not the model
file against the recorded hash (`src/cbbwp/serve.py:26-53`). The hash currently exists
only for humans (both registry hashes do verify — checked in this audit).

**Fix:** verify the hash at load (two lines, and it makes the manifest an integrity
check rather than a note); consider writing the training-run metadata into the manifest
at fit time instead of publish time.

### L2. The local calibration report on disk fires an alert, and predates the shipped model

`reports/calib_2026.json` (gitignored, local) has `"ok": false`: 40–20-min decile 5,
model 0.783 vs observed 0.760, z −3.1 over 2,995 games. It was generated at
2026-09-01T20:57Z — 26 minutes *before* the v2 manifest was created — so it likely
measures the pre-fix model. The docs do document the 40–20-min bucket as the worst
calibrated, but no doc mentions that the monitor's own thresholds already trip there.
**Fix:** re-run `calibration_monitor.py --source backtest --season 2026 --version v2`,
and either record the alert as a known finding or adjust the story. If it still fires,
that is the monitor doing its job on a real (documented) weakness, not noise — say so
somewhere findable.

### L3. Small record-keeping and lifecycle gaps in the poller/API

- The JSONL records only the **last** state per poll (`scripts/live_poller.py:142-159`);
  intermediate plays between polls are recoverable only by re-scoring. That is a
  documented design choice for the viz ("one point per poll"), but "the record of
  truth" phrasing oversells the file slightly; the truth is reconstructible, not stored.
- A game's final `status` transition is only recorded if it coincides with a new
  `(seq, wp)` key; the last JSONL row for a game can say `STATUS_IN_PROGRESS` forever.
- `Poller.last_emitted` and `LiveStore._latest`/`_history` grow without bound over a
  long-running process (one entry per game ever seen; trivial at season scale, but
  `/games` serves every game since startup, not the current slate).

### L4. Container/tooling nits

- `smoke_live.py` step 3 inside the Docker image FAILs (not SKIPs) because the image
  installs no `pytest`; docs say run smoke on the host, but the failure mode is
  misleading if someone tries.
- `deploy/Dockerfile` copies `pyproject.toml` then installs dependencies by hand; the
  file is unused.
- `scripts/fetch_data.py` downloads ~527 MB over `urlretrieve` with no timeout and no
  checksum; the entire model provenance rests on trusting the hoopR GitHub repo at
  fetch time. A recorded sha256 per parquet in-repo would make "rebuilt byte-identically"
  independently checkable.

### L5. Test-name overclaim

`tests/test_replay_harness.py:60` `test_out_of_order_and_duplicate_events_are_absorbed`
shuffles events but never introduces a duplicate; duplicates are untested (and
`build_states` would happily produce two states for a duplicated `seq`). Duplicates
cannot arise from the current adapter (dense re-numbering), so the behaviour is fine —
the test name promises more than the test checks. Rename or add the duplicate case.

## What was checked and found sound

Worth recording, since an audit that only lists problems misrepresents the codebase:

- **Headline metrics reproduce.** `scripts/evaluate.py` regenerates the README table
  exactly (log loss 0.3103 / Brier 0.1008 / acc 85.20% / ECE 0.0026; ESPN worse in all
  six buckets, on rows where ESPN's number is present — which is 100% of test rows).
- **Registry integrity.** Both manifests' hashes match their `model.txt` (verified);
  v1 is genuinely refused at load and that refusal is tested.
- **Train/serve parity is real, not aspirational.** The vectorised Polars path, the
  canonical Python path, and the ESPN adapter path are asserted equal on real games,
  down to identical win probabilities through the full service
  (`test_parity.py`, `test_espn_adapter.py`, `test_replay_harness.py`) — and these
  tests actually ran here (data present, nothing skipped).
- **Leakage discipline holds where I probed it.** Ratings are fit strictly before each
  game's date; team stats are shifted cumulative sums; season-level splits are clean;
  early stopping uses 2024 only; the possession-truth tests check the *rules of
  basketball*, not implementation-vs-implementation.
- **The state rules versioning story** (`STATE_RULES_VERSION`, manifest stamp,
  load-time refusal) is correctly implemented end to end.
- **The 2026-09-03 ordering fix** is correctly reflected everywhere I looked: the
  adapter preserves array order, the fixtures deliberately synthesise the
  nearly-monotonic `sequenceNumber` that would catch a regression, and the viz steps
  by clock while preserving feed-order probabilities.
- **The honest-negative results** (calibrator, endgame overrides beyond clamps, endgame
  table) are as documented: built, measured against pre-registered bars, not wired into
  serving. `serve.py` imports only `endgame.apply` — the clamps — as claimed.
- **The API and viz servers** are stdlib, localhost-bound by default, read-only, and
  escape user-controlled strings in the page; no injection or traversal path found
  (game ids are forced to `int` everywhere they touch a path or URL).

## Endgame estimation scripts (deep-dive findings beyond H2)

A separate pass covered the endgame estimation/build/validate/blend scripts, the report
builders, and the remaining tests. Beyond H2 above:

**Medium**

- **`scripts/blend_endgame.py:193-217` — the ship-criteria comparison is not
  apples-to-apples.** `p_blend` has the rule clamps applied, but the `model_only`
  baseline is the raw booster — while the shipped path applies clamps to the model.
  Re-measured for this audit: inside 60s on the test seasons the clamps move the model
  from 0.124624 to 0.124812, so the shipped-consistent comparison is
  0.124812 → 0.124130 ≈ **0.55% relative**, not the reported 0.40%. Still under the 1%
  bar, so the "does not ship" verdict survives — but the recorded number is wrong, and
  the `--tune` step optimises the unclamped objective that `--test` doesn't measure.
  Side-observation worth recording: this measurement shows the *shipped* clamps mildly
  worsen test log loss inside 60s (~+0.15% relative), consistent with EXPLAIN §7.8's
  "~0.0002" admission.
- **`scripts/calibrate_and_eval.py:21-23`** re-scans margins from the states parquets
  and zips them positionally against `test_preds.npz` with only a `len()` assertion —
  no `game_id` alignment check (`rebuild_test_preds.py:65-66` does this correctly). A
  future change in collect ordering silently corrupts this diagnostic.

**Low**

- `estimate_endgame_possessions.py:80-83` — a game's leading unknown-possession run has
  null `first("possession")` and falls to `otherwise(-margin)`, silently attributed to
  the away side.
- `estimate_endgame_params.py:137-145` — `prev_*` columns use a global `shift(1)` that
  leaks across game boundaries; currently masked by the `> 8`-row new-trip guard, but
  fragile.
- `estimate_endgame_params.py:195,217` — a trip's FT rows can classify as different
  `kind`s (first row `and_one`, second `two_shot`), splitting counts across the FT-rate
  cells.
- `tests/test_monitor.py:94` — `assert not monitor.check(...).ok or True` is vacuously
  true; a dead assertion dressed as a check (the assertions below it do the real work).
- `tests/test_endgame_sim.py:58-61` — the "criterion 3, exhaustively" test asserts
  margin-monotonicity of the *published* table, which `build_endgame_table.py:89` has
  already isotonic-projected along margin — it cannot fail by construction. The honest
  signal is `isotonic_max_correction` in the manifest, which the test does not bound.
- `scripts/build_source_bundle.py:22` — the "complete source" recovery bundle excludes
  `build_source_bundle.py` itself.
